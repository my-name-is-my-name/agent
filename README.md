# MRO Assessment Agent — версия 0.1

Отдельный локальный агент на LangGraph. Принимает текст заявки, уточняет объект и задачу, вызывает существующий квалифицированный поиск аналогов, читает доступные документы через API и формирует предварительную карточку с цитатами. Интерфейс — Open WebUI; журнал фактических действий выводится в reasoning.

Существующие проекты не импортируются и не изменяются. Массовой векторизации и прямого доступа к исходным папкам нет. Агент не рассчитывает часы и не выдаёт решение «брать / не брать» в версии 0.1. Извлечённые моделью факты и гипотезы требуют проверки инженером.

## Запуск

Требуется Python 3.12. Создайте отдельное окружение в этой папке:

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install -c requirements.lock -e '.[test]'
```

Создайте локальный `.env` на основе `.env.example`. Укажите реальные локальные API, название модели, длинный случайный токен и разрешённые ID пользователей Open WebUI. Файл не включается в Git. `LLM_URL` должен включать `/v1`; `KB_URL` — базовый URL без `/api`. Локальная модель должна поддерживать JSON-ответы Chat Completions (`response_format=json_object`), контекст как минимум 32k токенов и ответ до 2400 токенов.

Пример запуска с переменными, уже установленными в окружении:

```bash
.venv/bin/uvicorn mro_agent.api:create_app --factory --host 127.0.0.1 --port 8140 --workers 1
```

Uvicorn не читает `.env` автоматически. Можно использовать подготовленный Compose, который передаёт `.env` сервису:

```bash
docker compose -f compose.yml up --build -d
```

Сборка скачивает зависимости; рабочие обращения идут только к настроенным локальным сервисам. В изолированном контуре используйте заранее подготовленные образ/пакеты. Compose публикует `127.0.0.1:3003` и подключает агента к существующей сети `intranet-rag_default`. Из Open WebUI в этой сети используйте `AGENT_URL=http://mro-assessment-agent:8140`; порт 8140 остаётся внутренним портом контейнера. Внутри контейнера `127.0.0.1` обозначает сам контейнер, поэтому адреса KB и LLM должны быть доступны именно из контейнера агента.

Compose хранит runtime в отдельном именованном томе. Не подменяйте его чужими базами. Один процесс агента блокирует runtime через файловый lock; запуск нескольких workers запрещён. SQLite хранится на локальном диске/томе с корректными блокировками (не сетевой общий NFS-каталог для рабочего развёртывания).

## Подключение Open WebUI

1. Администратор создаёт Pipe Function, вставляя исходник `openwebui/pipe.py`, и включает её для пилотной группы.
2. В Valves задаются `AGENT_URL` и `API_TOKEN`. Токен доступен только администратору и Pipe, не браузеру пользователя.
3. ID участников этой группы добавляются в `MRO_AGENT_ALLOWED_USERS`. Все участники первой версии должны иметь одинаковые права на используемый корпус. Передача `X-User-Id` в KB сама по себе не доказывает, что старый сервис реализует ACL.
4. Пользователь выбирает `MRO Assessment Agent` и создаёт обычный сохранённый чат. Один чат — одна заявка. Временные/анонимные чаты без идентификаторов не поддерживаются.
5. В первом сообщении пользователь описывает объект, проблему/работу и желаемый результат. Ответ на уточнение продолжает ту же оценку. Вопрос по карточке отвечает по сохранённым источникам, а исправление исходных данных повторно запускает исследование.

Pipe передаёт доверенный ID пользователя, `chat_id` и `message_id`, считывает оригинальный `user_prompt` до обёртки RAG Open WebUI, игнорирует служебные задания генерации заголовков/тегов. Вложения/изображения не анализируются; отсутствие обработки явно показывается. На версии WebUI без исходного `user_prompt` вложения отклоняются, чтобы их автоматически подставленный текст не превратился в заявку.

`reasoning_content` содержит только события выполнения; `content` — уточняющие вопросы и карточку. JSON SSE сохраняется до клиента, поэтому reasoning не превращается в обычный текст. `tool_calls` не выдаются: инструменты уже выполняются сервером агента.

Документация интерфейса: [метаданные Pipe](https://docs.openwebui.com/features/extensibility/plugin/development/reserved-args/), [reasoning](https://docs.openwebui.com/features/chat-conversations/chat-features/reasoning-models/), [прерывания LangGraph](https://docs.langchain.com/oss/python/langgraph/interrupts).

## Граф и ограничения

`analyze → [clarify → analyze] → search → read → extract → synthesize → finish`

- Блокирующее уточнение останавливает граф через `interrupt()`. После трёх неудачных циклов результат передаётся инженеру.
- Один проход поиска, до пяти принятых и пяти непринятых заявок. Принимаются только `qualified=true`; `weak_analog` никогда не дополняет выдачу.
- Для чтения выбираются три аналога по score сервиса, позиции выдачи и стабильному ID. До трёх документов на аналог. Приоритет у отчётов, инструкций и заключений; остальные — по ID.
- Читается до 12 000 символов одного документа, 48 000 на оценку, 24 фрагментов по 6000 символов. Порядок фрагментов берётся из API, весь документ прочитанным не объявляется. Пропуски и частичное чтение показываются.
- До 40 проверенных утверждений. Сначала проверяются точный ID источника и дословное вхождение цитаты, затем отдельный вызов модели проверяет смысловое соответствие. Это фильтр ошибок, а не формальная гарантия инженерной корректности.
- Гипотезы состава работ отделены от исторических фактов. Каждая ссылается на изученные основания; техническая применимость не предполагается.
- Документы никогда не превращаются в инструкции для вызова новых инструментов. В v0.1 маршрут задан графом, а список HTTP-операций фиксирован.

Состояние и журнал хранятся в SQLite. По завершении каждого шага сохраняется checkpoint; read-only вызовы незавершённого шага могут повториться после аварии. Очередь постоянная, worker отделён от соединения браузера. Закрытие вкладки не отменяет исследование. При повторной доставке того же `message_id` возвращается прежнее задание; другое содержимое с тем же ID возвращает 409. Пока оценка выполняется, новое сообщение той же заявки получает 409.

После перезапуска работа с очередью возобновляется. Обычное штатное завершение ждёт worker 5 секунд; при принудительном завершении незаконченная работа восстанавливается из checkpoint. Ошибки модели, неполученные документы и пустой поиск видны в ограничениях, а не маскируются под подтверждение/отказ.

## HTTP API

Кроме `/health` и статической схемы API, все прикладные маршруты требуют `Authorization: Bearer <service-token>` и `X-User-Id: <allowed-user-id>`. Токен даёт доверенному адаптеру право утверждать личность пользователя, поэтому его нельзя выдавать участникам пилота. Чужие карточки и задания отвечают 404.

| Маршрут | Назначение |
|---|---|
| `GET /health` | Статус процесса/worker без вызова чужих health endpoints |
| `GET /v1/models` | Модель `mro-assessment-agent` |
| `POST /v1/chat/completions` | Чат, SSE или обычный JSON; обязательны `chat_id`, `message_id` |
| `POST /api/assessments` | Создание/продолжение через `{request, chat_id, message_id, attachments_present}`; 202 + job ID |
| `POST /api/assessments/{id}/answers` | Ответ с проверкой владельца и связи чата |
| `GET /api/assessments/{id}` | Карточка с историей результатов |
| `GET /api/jobs/{id}` | Состояние задания и результат |
| `GET /api/jobs/{id}/events?after=0` | Журнал с последовательными ID |

Нестандартные идентификаторы чата нужны для состояния, поэтому для Open WebUI поставляется Pipe, а не предполагается автоматическая передача метаданных обычным подключением провайдера.

В v0.1 интерфейс адресован ограниченному пилоту. Предоставьте корпус с одинаковыми разрешениями для группы. Для масштабирования нужны групповые ACL upstream, ограничение нагрузки и сроков хранения; для требований ТЗ о шифровании — шифрованный диск/том и защищённый транспорт. Поставляемая SQLite сама не шифрует содержимое. Внешняя трассировка не включается. На сетевом уровне рабочий контур должен запрещать внешние соединения: программная проверка приватных адресов не заменяет egress policy.

## Проверка существующих сервисов

Клиенты повторяют интерфейсы, найденные в исходном коде `mro_kb_platform`:

- `POST /api/similar-cases/search`: `query`, `context`, `limits`; используется квалифицированный путь, без `legacy_ranked_query`.
- `POST /api/case-facts`: разрешение ID. Сейчас подтверждён только `EXACT_INTERNAL_ID`; `UNRESOLVED` и неоднозначные результаты останавливают чтение этого аналога. Текст, сгенерированный этим endpoint, не подменяет чтение оригинальных фрагментов.
- `GET /api/cases/{id}`: перечень документов.
- `GET /api/documents/{id}`: поля документа и `chunks` с текстом. Проверяется принадлежность документа выбранной заявке.

Коммерческие ID могут отсутствовать в корпусе завершённых работ. В таком случае агент сообщает, что документы аналога не разрешены; он не угадывает связь по номеру и не подменяет источник. Для расширения покрытия требуется подтверждённое сопоставление в существующем сервисе или его отдельном адаптере.

Работающие производственные API и LLM не вызываются автоматически при установке/тестах. Перед пилотом администратор должен указать разрешённый тестовый корпус и выполнить smoke-сценарий с инженером. Исходные реальные заявки, отчёты и данные истории не передаются во внешние среды разработки.

## Тесты

```bash
.venv/bin/python -m pytest -q
```

Тесты используют синтетические ответы инструментов и настоящий LangGraph с SQLite: полный маршрут, пауза и продолжение после перезапуска, точные цитаты и их отклонение, ограничения чтения, пустые аналоги, недоступность сервиса, неподтверждённые связи ID, права доступа, дубли, повторный вопрос и исправление заявки, очередь, SSE и повтор готового результата.

Перед открытием пилота вручную проверить отображение reasoning, восстановление того же чата, доступность ссылок/идентификаторов документов для инженера, задержки локальной модели и пригодность аналогов. Метрики ТЗ не объявляются достигнутыми по модульным тестам.

### Результат проверки реализации

14 сентября 2026: Python 3.12.14, библиотеки из `requirements.lock`, **26 тестов пройдены**. Прогон включал настоящий LangGraph/SQLite, синтетические инструменты, HTTP MockTransport и FastAPI TestClient. Единственное предупреждение — устаревающий alias BlockingPortal внутри Starlette/AnyIO.

В ограниченной среде разработки TestClient не мог запуститься из-за запрета `socketpair`; полный успешный прогон выполнен вне этого ограничения. В рабочие сервисы запросы не отправлялись, контейнер не развёртывался, Pipe в рабочий Open WebUI не устанавливался. Контракт клиентов сверялся с исходным кодом существующих сервисов; проверка их фактического развёртывания и приёмка инженером остаются шагами пилота.

Созданное при разработке `.venv` использует временную установку Python в `/tmp` и предназначено для проверки. Для постоянного запуска пересоздайте окружение со штатным Python 3.12 или используйте Docker; runtime и зависимости не следует привязывать к временному интерпретатору.
