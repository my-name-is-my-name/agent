# Поэтапное развитие по ТЗ

## 0.1 — минимальный агент

Отдельный проект, LangGraph, Open WebUI, поток событий в reasoning, уточнения с сохранением состояния, существующий квалифицированный поиск аналогов, чтение доступных документов через API, карточка с источниками и гипотезами. Код реализуется в этом выпуске; допуск к пилоту требует проверки инженером на настроенных локальных сервисах.

## 0.2 — исследование ссылочных документов

Подключить существующие ecar_search и geometry_search через проверенные API; переиспользовать адаптеры discovery из mro_docs_kb без прямого доступа агента к каталогам. API сервисов сверяются перед интеграцией. Добавить извлечение ссылок, прямой поиск по новой заявке при отсутствии аналогов, проверку номера/ревизии/статуса/применимости, разрешённую конвертацию через convert и получение текста через сервис документов.

Начальные пределы: два дополнительных цикла, глубина ссылок два, пять новых документов на оценку. Сохранять ID конвертации до ожидания, повторно использовать ту же версию результата. Чтение графики чертежей передавать инженеру при отсутствии проверенного визуального модуля. Ни общая векторизация, ни чтение всех ссылок не обязательны.

Приёмка: путь от ссылки в отчёте до подтверждённого фрагмента, отсутствие подмены ревизий, отсутствие дублей заданий после перезапуска, явные неизвестная применимость и недоступные документы.

## 0.3 — трудоёмкость

После получения пути к истории обследовать смысл часов (план/факт/длительность), состав работ, идентификаторы и коэффициенты. Метод расчёта согласовать по фактической структуре файла. Отдельный Labor Estimation API читает историю; агент передаёт структурированный план и аналоги. Часы считает программа, не LLM.

Результат: диапазон, методика, исходные строки и версия файла, состав покрытых работ, актуальные коэффициенты и ограничения. Исключить повторное добавление менеджмента/проверки. При недостаточных данных — явный отказ от численной оценки. Проверка на отложенной истории без утечки фактических часов оцениваемой заявки.

## 0.4 — полный цикл оценки по ТЗ

Подключить ATA-анализ и контролируемые правила capability, подтверждённые блокирующие условия, применимость и маршрут одобрения. Добавить зависимости работ, документы к выпуску, приём связанных файлов через API, фиксацию письма-источника, рекомендацию и явное решение сотрудника с комментарием.

Ошибка инструмента не означает «брать» или «не брать». Исторические документы подтверждают опыт, а не актуальную применимость. Автоматическая отправка писем, расчёт цены и выпуск коммерческого предложения остаются вне задач.

## Сквозная приёмка

Наборы разработки, калибровки и окончательной оценки не пересекаются. Отдельно измеряются качество ответов с источниками, негативные сценарии, экономия времени подготовки оценки, пользовательская оценка, доступность и требования ИБ из ТЗ. Групповые ACL, шифрование и мониторинг доводятся до требований рабочего контура до общего развёртывания. Достижение этих показателей не следует из наличия кода или прохождения синтетических тестов.
